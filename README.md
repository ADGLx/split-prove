# Split-Prove

Split-Prove is a proof-of-concept for Midnight zswap delegated proving. The goal is to let a wallet outsource the expensive spend proof to a proof server without sending the raw zswap secret key (`sk`) to that server.

The wallet proves only the relations that require `sk`. The proof server proves the coin commitment, Merkle membership, nullifier insertion, value commitment, and spend rules from public handoff data. A patched node verifies all proofs and checks that their shared public inputs match before accepting the transaction.

## How It Works

```mermaid
flowchart LR
    subgraph LOCAL["Local wallet / client"]
        W["sk, r, salt"]
        C["coin + zswap Merkle witness"]
        R["synthetic registry witness"]
        A["π_attest<br/>off-chain first registration"]
        S["π_sk<br/>public: nullifier,<br/>coinBindingTag, registryRoot"]
        H["split handoff<br/>coin metadata, pk,<br/>commitmentHash, nullifier,<br/>coinBindingTag, registryRoot, π_sk"]

        W --> A
        W --> R
        W --> S
        C --> S
        R --> S
        S --> H
        C --> H
    end

    subgraph SERVER["Proof server"]
        P["π_spend<br/>public: coinBindingTag,<br/>registryRoot"]
    end

    subgraph NODE["Node"]
        V["Verify π_sk and π_spend"]
        M["Check registryRoot"]
        D{"Accept?"}
        OK["Admit"]
        NO["Reject"]

        V --> M --> D
        D -- yes --> OK
        D -- no --> NO
    end

    H -- "public handoff, no sk/r" --> P
    P -- "v4 split proof bundle<br/>(π_sk, π_spend, coinBindingTag, registryRoot)" --> V
```

There are two proofs in the current v4 split bundle:

- `π_sk`, generated for each spend, proves the wallet knows an `sk` whose synthetic registry leaf is under `registryRoot`, proves the canonical zswap nullifier was derived from that `sk` and the coin, and proves the coin-binding tag was derived from the coin and `pk`.
- `π_spend`, generated by the proof server, proves the coin commitment was built from the coin and `pk`, proves that commitment is in the Merkle tree, proves the declared nullifier is inserted, and proves the value commitment and spend rules are valid.

The wallet attestation proof is still generated as off-chain first-registration evidence for the local POC, but it is not carried in the split bundle. At submission time the node verifies the v4 bundle public inputs `coinBindingTag` and `registryRoot`; the local stack installs a permissive registry-root checker.

The important privacy change is that `pk`, `C_sk`, and `coinCommitment` no longer appear in the on-chain split public inputs. Per spend, the wallet proves the canonical nullifier and registry-membership relation while preserving normal double-spend semantics.

## Running The E2E

The main demo runs a full split-send against the local Midnight stack:

```bash
make e2e
```

One-time setup:

```bash
npm install
make local-install
cp .env.example .env
make rebuild-images
```

Start the local node/indexer/proof-server stack in another terminal:

```bash
make local-nodes
```

Use local-dev option 6 to fund the split-prove wallet before running `make e2e`. The demo scans for the funded shielded output, creates the wallet attestation and per-spend client proof, calls `/v2/prove-split-spend`, assembles the split transaction, Dust-balances it, submits it to the rebuilt local node, and waits for inclusion. Both node and indexer must be rebuilt against the patched ledger; the helper only accepts localhost local-dev endpoints.

The current split-prove demo supports user-owned shielded coins only. Contract-owned split spends are rejected by the proof-server and SDK preimage builder.

More run details, environment variables, and endpoint shapes live in [docs/poc-runbook.md](docs/poc-runbook.md).

## Compatibility And Privacy

This PoC requires the patched ledger, node, and indexer. Stock hosted nodes do not know how to decode or verify the v4 split proof bundle or client derivation proof, so they reject split-send blocks.

The PoC is designed to protect the raw `sk` from the proof server, but it is not a final privacy design. The current local POC uses a permissive registry-root checker and a synthetic client-side registry witness; a production design would replace that local checker with a real registry admission policy.
